# 直播电商中台项目设计状态与约束

更新日期：2026-06-14

## 1. 项目定位

本项目是《信息系统分析与设计》课程验收用的企业内部直播电商业务中台。系统不承担消费者下单、支付、物流履约的前台交易功能，而是接收外部平台和内部岗位产生的数据，支撑选品、采购、库存、直播执行、售后与运营复盘。

内部操作角色：

- 管理层：查看数据总览、报告、主播绩效和全局指标。
- 运营人员：维护直播场次、商品、脚本、选品和售后。
- 采购人员：查看选品结果、采购建议、采购单和供应商。
- 仓储人员：查看库存和预警。
- 主播：查看直播脚本、监控和个人表现。
- 系统管理员：维护账号、权限和基础配置。

外部实体：

- 消费者：产生订单、互动、行为和售后数据。
- 供应商：提供候选商品、成本、库存和履约周期。
- 直播平台：提供直播场次、在线人数、弹幕、点赞、加购和成交数据。
- 支付/物流平台：提供支付状态、发货、签收和退货数据。

## 2. 当前技术架构

当前实现保持前后端分离的单体架构：

- 前端：Vue 3 + TypeScript + Vite + Pinia + Vue Router。
- 后端：Express + TypeScript + Knex。
- 数据库：Microsoft SQL Server。
- 实时推送：SSE，用于直播监控的指标、订单、弹幕、情绪、AI 洞察和话术建议。
- 图表：Chart.js + vue-chartjs。
- 认证：JWT + bcryptjs。
- LLM：OpenAI 兼容接口；无 API Key 时必须有本地 fallback。
- 新品冷启动：候选池商品的相似品、品类趋势、供应履约、库存、毛利和试播反馈综合评估。

架构约束：

- 不拆微服务。课程项目和本地部署优先，保持单进程后端和单数据库。
- 新增业务逻辑优先放在 `server/src/services`，路由只做参数解析和响应。
- 前端页面只组合组件和业务状态，跨页面通用能力放到 `client/src/components` 或 `client/src/utils`。
- 验收数据必须可重复运行，优先使用 `npm run seed:acceptance`。

## 3. UI 设计系统

本项目沿用原设计文档中的“纸墨金朱”风格：

- 页面背景：纸色 `--paper`。
- 卡片背景：纸色深 `--paper-dark`。
- 主文字：墨色 `--ink`。
- 辅助文字：`--ink-soft`。
- 主强调/风险/实时状态：朱砂 `--vermillion`。
- 正向状态：`--success`。
- 信息状态：`--info`。
- 边框和分割：`--rule` / `--rule-soft`。

UI 约束：

- 不做营销式首页，登录后直接进入业务界面。
- B 端页面保持信息密度，优先表格、筛选、状态、图表和操作路径。
- 卡片用于承载指标、图表、列表分组，不嵌套卡片。
- 页面标题使用中文业务名，副标题说明数据口径或任务用途。
- 表格列头默认可排序，首次点击按降序排列；操作列不排序。
- 状态必须视觉分层。直播场次使用“进行中/已排期/已结束”三类状态卡、表格色条和状态徽章。
- 左侧导航只放一层主要业务模块；直播监控不作为一级入口，必须从直播场次进入具体场次。
- 库存管理是供应链风险主入口；采购管理放在库存管理之后，定位为采购单台账、状态流转和新品采购入口。

## 4. 数据口径

运营数据总览当前口径：

- KPI、销售趋势、主播 TOP5：以数据库最大订单日期为截止日的近 30 天。
- 环比：近 30 天对比前 30 天。
- 库存告警：当前库存快照，不做时间区间累计。
- 库存规划：以当前库存、在途采购、供应商交期、近 90 天销量、未来直播需求、商品潜力和新品状态计算动态补货点。

直播监控当前口径：

- 顶部计时器：前端本地 1 秒刷新，SSE 指标到达时校准。
- 在线人数趋势：接收后端 `metrics` 事件后追加数据点，最多保留 60 个点。
- 弹幕情绪：后端批量分析弹幕后推送百分比分布。

新品冷启动当前口径：

- 问题边界：不做全网爆品发现，只处理已经进入候选池或商品库的新品。
- 页面识别：选品分析列表同时展示 `在售` 与 `待评估` 商品，`待评估` 明确标记为新品。
- 入口约束：冷启动评估只作为新品专项分析入口，不替代老品常规五维评分。
- 初评依据：相似商品、品类趋势、供应商履约、库存保障、毛利空间和已有试播信号。
- 探索加权：新品早期可获得临时加权，随上架时间和试播次数衰减。
- 决策输出：加码试播、建议试播、继续观察、暂缓投放。
- 执行建议：主播、时段和话术方向用于试播，不替代运营最终决策。

数字顾问报告当前口径：

- 默认不展开，运营或管理层点击“生成顾问报告”后按当前数据库状态生成。
- 报告不模拟外部咨询结论，只输出本系统能由商品、库存、供应商和表现数据推导出的管理摘要、行动项、加码商品、新品观察、品类机会和风险提醒。

库存采购闭环当前口径：

- 库存管理展示动态风险，不只显示安全库存。
- 一键采购从库存行直接创建待审核采购单，系统给默认建议量，用户可以修改数量、采购价和预计到货时间。
- 采购管理弱化为采购单状态流转、采购建议查看和新品采购。
- 新品采购会创建 `待评估` 商品、默认 SKU、默认库存记录和待审核采购单，后续进入选品冷启动流程。

主播商品适配与带货计划当前口径：

- 问题边界：系统负责在已有商品库、主播库和直播场次基础上，辅助判断“哪个主播更适合带哪个商品”以及“某一场直播可以带哪些商品”。不承担全网主播招募、合同结算、主播档期冲突求解和分钟级导播编排。
- 输入数据：主播品类专长、粉丝规模、历史转化、互动率、停留时长、脚本执行评分、商品毛利、库存、商品历史 GMV、退款率、新品冷启动状态和场次品类。
- 决策输出：`AnchorProductFit` 形成主播-商品适配表，输出适配分、A/B/C 等级、主推/辅推/试播/暂缓角色、推荐理由和风险说明。
- 执行输出：`LivePlan` 与 `LivePlanItem` 形成场次级带货计划，输出商品顺序、建议角色、建议讲解时长、目标 GMV、目标订单和脚本引用。该计划是草案，需要运营人员结合实际资源确认。
- 闭环关系：适配表用于直播前排品，直播执行后由直播复盘模块沉淀商品与主播表现，再反向影响下一轮适配评分。

- 主播-商品适配评分、适配表与场次带货计划。

## 6. 后续修改规则

新增或修改功能时需要同时检查：

1. 是否有明确的业务角色和操作路径。
2. 是否能说明外部输入、处理过程、数据存储和输出。
3. 是否保持 UI 的纸墨金朱风格和 B 端信息密度。
4. 是否有可重复的数据或测试命令支撑验收。
5. 是否更新本文件或 `docs/acceptance` 下的相关验收材料。
